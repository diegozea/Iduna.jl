# Parallel ThorAxe Sampling Report

## Summary

Iduna schedules PID samples on Julia threads, but serializes the complete
ThorAxe calls, including `transcript_query`. ThorAxe.jl activates Conda by changing
the process environment, so overlapping wrappers can corrupt `ENV` and Conda's
state. One shared lock covers activation, the command runner and environment
restoration. The current runner waits for the command to finish before returning.

This protects ThorAxe calls made through Iduna. Other code that changes the process
environment or current directory, including direct ThorAxe/CondaPkg calls, does not
share this lock. Independent work directories do not remove that limitation.

The implementation uses Julia's built-in `Base.Threads.@threads` macro with the
`:greedy` scheduler. Assembly and HHsuite scoring can still overlap. Each sampled
ThorAxe run writes to its own temporary run
directory, log files, sampled species file, FASTA file, Stockholm file, and
HHsuite log label. Sample scores are collected in preallocated sample-number
slots, so `scores.csv` remains ordered by sample number even if samples finish in
a different order.

## How to Use It

For an installed `iduna` app, set Julia threads with an environment variable:

```bash
JULIA_NUM_THREADS=4 iduna P20963 --mmseqs-db /path/to/mmseqs/db --mmseqs-threads 8
```

or pass Julia flags before the app separator:

```bash
iduna --threads=4 -- P20963 --mmseqs-db /path/to/mmseqs/db --mmseqs-threads 8
```

From a source checkout, start Julia with more than one Julia thread:

```bash
julia --threads 4 --project=. -m Iduna P20963 --mmseqs-db /path/to/mmseqs/db --mmseqs-threads 8
```

The same idea works when using Julia directly:

```bash
julia --threads 4 --project=.
```

Then run Iduna as usual:

```julia
using Iduna

result = iduna("P20963"; mmseqs_db="/path/to/mmseqs/db", workdir="P20963")
```

You can also set the thread count before starting Julia:

```bash
JULIA_NUM_THREADS=4 julia --project=. -m Iduna P20963 --mmseqs-db /path/to/mmseqs/db --mmseqs-threads 8
```

This setting affects the ThorAxe sampling step. The Iduna app option
`--mmseqs-threads` is different: it controls MMseqs2 during the expansion step.
Do not put `--threads` after the Iduna arguments; it is a Julia runtime flag,
not an Iduna option.

## Historical Scheduling Experiment

I used a temporary benchmark script outside the package tree. It was not added
to the repository. The script exercised Iduna's `_score_pid_candidates` path with
one PID and 12 PID samples. The ThorAxe call was replaced by a controlled fake
runner that slept for 0.12 seconds for each sampled run and then wrote the small
ThorAxe-like files needed by Iduna's MSA assembly code. This isolates the
parallel scheduling behavior without depending on network access or a large
live ThorAxe input bundle. These timings predate serialization of ThorAxe calls
and do not measure safe throughput with the real environment wrapper.

Each thread count used a fresh Julia process, a warm-up call, and three timed
repetitions. The experiment ran on this Linux workstation with Julia 1.12.6.

| Julia threads | Times (s) | Median (s) | Speed-up vs 1 thread |
|:--|:--|--:|--:|
| 1 | 1.499, 1.499, 1.500 | 1.499 | 1.00x |
| 2 | 0.753, 0.757, 0.753 | 0.753 | 1.99x |
| 4 | 0.382, 0.380, 0.407 | 0.382 | 3.93x |
| 8 | 0.255, 0.255, 0.256 | 0.255 | 5.88x |

## Conclusions

The historical fake-runner experiment demonstrated scheduling speedup. It does
not justify a thread-count recommendation or predict current ThorAxe throughput.
Serialization deliberately gives up simultaneous ThorAxe execution for correct
environment restoration. Measure representative workloads before tuning threads
or replacing this boundary with a per-command environment implementation.

The package tests cover the threaded score collection path and check that the
per-PID score CSV remains ordered by sample number. Separate regressions exercise
the actual ThorAxe/Conda wrapper, blocked overlapping calls, runner failures and
restoration of the environment and current directory.
